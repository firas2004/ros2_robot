Navigation autonome

Implémentation et analyse comparative d'une Machine à États Finis (FSM) et d'un Behavior Tree (BT) pour l'évitement d'obstacles en simulation Gazebo.

Ubuntu 22.04 LTS ROS2 Humble TurtleBot3 Waffle

01 — Introduction

Vue d'ensemble de
l'environnement

Ce TP met en œuvre un robot mobile autonome dans un simulateur physique 3D. Le robot navigue sans intervention humaine, détecte les obstacles grâce à un capteur laser, et prend ses décisions en temps réel.

🤖
TurtleBot3 Waffle
Robot à deux roues motrices, populaire en recherche académique. Équipé d'un Lidar 360°, d'une caméra RealSense et d'une unité IMU. Modèle réel simulé fidèlement dans Gazebo.
🌍
Gazebo Classic
Simulateur physique 3D open-source. Modélise la gravité, les collisions, la friction et les capteurs. Le plugin GazeboRosFactory assure le pont avec ROS2 pour spawner les entités.
📡
ROS2 Humble
Middleware robotique distribué. Les nœuds communiquent via des topics (pub/sub). Le Lidar publie sur /scan, le contrôleur souscrit et publie sur /cmd_vel.
🔦
Lidar 360°
Capteur laser tournant qui mesure les distances à 360° autour du robot. Publie un message LaserScan contenant un tableau de distances toutes les ~200ms (5 Hz).

Fig. 1 — Architecture générale du système de navigation autonome. Les topics ROS2 /scan et /cmd_vel assurent la communication entre les composants.

02 — Module Lidar

Analyse multi-zones
du capteur laser

Le module lidar_zones.py divise les 360° du Lidar en 6 zones angulaires distinctes, permettant une prise de décision plus fine qu'une simple lecture frontale.

Fig. 2 — Découpage en 6 zones angulaires du Lidar 360°. Les anneaux indiquent les seuils DIST_AVOID (0.45m) et DIST_WARN (0.70m).

FRONT_RIGHT

90°–150° — Flanc gauche

Évitement progressif — speed_factor
La distance frontale génère un facteur entre 0 et 1. Entre DIST_AVOID (0.45m) et DIST_WARN (0.70m), la vitesse diminue progressivement. En dessous de 0.45m, arrêt total. Au-delà de 0.70m, pleine vitesse. Cela évite les freinages brusques.

03 — Version 1

Machine à États Finis
(FSM)

La FSM modélise le comportement du robot comme un automate. À chaque instant, le robot est dans un seul état, et des conditions (basées sur les données Lidar) déclenchent les transitions.

FORWARD TURN_LEFT TURN_RIGHT BACK_UP STUCK

Fig. 3 — Diagramme d'états de la FSM. Les transitions en pointillés indiquent un retour vers l'état FORWARD (voie libre). Les transitions en rouge signalent des mécanismes anti-blocage.

Description des états

ÉtatComportement
FORWARDAvance à vitesse proportionnelle au speed_factor
TURN_LEFTRotation pure gauche. Rapide si obstacle dur, lente si avertissement
TURN_RIGHTRotation pure droite. Même logique que TURN_LEFT
BACK_UPRecule à basse vitesse quand les deux côtés sont bouchés
STUCKRecul + rotation forcée pendant STUCK_DURATION secondes

Améliorations FSM

Anti-oscillation
Un historique des OSC_WINDOW derniers états est maintenu. Si plus de OSC_THRESHOLD alternances TURN_LEFT↔TURN_RIGHT sont détectées, la gauche est forcée pour casser la boucle.
Anti-blocage (STUCK)
Si le robot n'avance pas depuis plus de STUCK_TIME_S secondes, il entre en état STUCK : recul + rotation à ANGULAR_STUCK pendant STUCK_DURATION secondes.

Extrait de code — transition FSM

# Calcul du prochain état selon l'analyse Lidar
def _compute_next_state(self, a: dict) -> str:
    if a["avoid_direction"] == "back":
        return STATE_BACK_UP
    if a["obstacle_front"]:
        if a["avoid_direction"] == "left":
            return STATE_TURN_LEFT
        return STATE_TURN_RIGHT
    # Avertissement précoce → correction douce
    if a["warn_front"] and not a["warn_front_left"] and a["warn_front_right"]:
        return STATE_TURN_LEFT
    return STATE_FORWARD

04 — Version 2

Behavior Tree
(BT)

Le Behavior Tree organise les décisions en un arbre de nœuds évalués à 10 Hz. Chaque nœud retourne SUCCESS, FAILURE ou RUNNING. L'arbre est traversé de haut en bas, du premier enfant vers le dernier.

Séquence →
Exécute ses enfants dans l'ordre. S'arrête dès qu'un enfant retourne FAILURE. Succède si tous réussissent.
Sélecteur ?
Essaie ses enfants dans l'ordre. S'arrête dès qu'un enfant retourne SUCCESS. Échoue si tous échouent.
Feuilles
Conditions (vérifient l'état du monde) et Actions (interagissent avec le robot). Retournent SUCCESS, FAILURE ou RUNNING.

Fig. 4 — Structure du Behavior Tree. Le sélecteur racine évalue les branches par ordre de priorité. Chaque séquence exige que TOUTES ses conditions soient vraies avant d'exécuter son action.

Nœuds implémentés

NœudTypeRôle
IsStuckConditionVérifie si le robot est bloqué depuis plus de STUCK_TIME_S secondes
BackupAndSpinActionRecule + tourne en RUNNING pendant STUCK_DURATIONs, puis retourne SUCCESS
IsObstacleAheadConditionRetourne SUCCESS si obstacle_front == True (seuil dur)
TurnAwayActionCalcule la direction (gauche/droite/reculer) selon avoid_direction
IsWarningConditionRetourne SUCCESS si warn_front == True ET obstacle_front == False
SlowDownActionAvance avec speed_factor et correction angulaire douce
DriveForwardActionAvance à pleine vitesse, toujours SUCCESS
Blackboard py_trees 2.x
Sous ROS2 Humble, l'API Blackboard a changé. Il faut impérativement utiliser py_trees.blackboard.Client avec register_key(). Les données Lidar analysées (lidar_analysis) et le chrono anti-blocage (stuck_since) sont partagés entre tous les nœuds de l'arbre.

05 — Analyse comparative

FSM vs Behavior Tree

Les deux approches produisent un comportement équivalent mais différent dans leur architecture, leur maintenabilité et leur extensibilité.

Critère FSM BT
Structure Automate fini : états + transitions explicites. Tout le logique dans _compute_next_state(). Arbre de nœuds hiérarchiques. Chaque nœud est une classe Python indépendante.
Lisibilité Facile à tracer à la main. Diagramme d'états naturel. Peut devenir complexe avec de nombreuses transitions. Structure visuelle claire grâce à l'arbre. Chaque comportement est isolé et nommé.
Extensibilité Ajouter un état = modifier _compute_next_state() et _execute_state(). Risque de régression. Ajouter un comportement = créer une nouvelle classe + l'insérer dans l'arbre. Pas de modification de l'existant.
Priorités Implicites dans les if/elif de la fonction de transition. Explicites : l'ordre des enfants du sélecteur = la priorité. Visible directement dans la structure.
Réutilisabilité Les comportements sont couplés à la classe principale. Chaque nœud feuille est réutilisable dans d'autres arbres ou projets.
Débogage Logger l'état courant suffit. Simple. py_trees fournit des outils de visualisation de l'arbre en temps réel.
Performance Légèrement plus rapide : pas de traversée d'arbre. Overhead minimal (traversée en mémoire). Négligeable à 10 Hz.

07 — Mise en œuvre

Instructions de
compilation et d'exécution

⚠ Erreur fréquente — Service /spawn_entity unavailable
Cette erreur survient si Gazebo n'a pas eu le temps de charger complètement avant que le script de spawn ne soit appelé. Solution : attendre que le robot soit visible dans la fenêtre Gazebo avant de lancer le nœud de navigation. Sur les machines lentes, ce délai peut aller jusqu'à 60 secondes.

1. Installation des dépendances

# Package TurtleBot3 pour Gazebo (ROS2 Humble)
sudo apt install -y ros-humble-turtlebot3-gazebo

# py_trees (obligatoire pour le BT)
sudo apt install -y ros-humble-py-trees ros-humble-py-trees-ros \
                   ros-humble-py-trees-ros-interfaces

# Variable d'environnement — à ajouter dans ~/.bashrc
export TURTLEBOT3_MODEL=waffle

2. Compilation

cd ~/ros2_ws/src
cp -r /chemin/vers/turtlebot3_nav .

cd ~/ros2_ws
colcon build --packages-select turtlebot3_nav
source install/setup.bash

3. Lancement (méthode recommandée)

# Terminal 1 — Gazebo (attendre que le robot soit visible)
export TURTLEBOT3_MODEL=waffle
ros2 launch turtlebot3_gazebo turtlebot3_world.launch.py

# Terminal 2 — FSM OU BT (après apparition du robot)
source ~/ros2_ws/install/setup.bash
ros2 run turtlebot3_nav fsm_navigation   # Version FSM
# OU
ros2 run turtlebot3_nav bt_navigation    # Version BT

4. Vérification

# Vérifier que le Lidar publie (doit afficher "average rate: 5.0")
ros2 topic hz /scan

# Voir les commandes envoyées au robot (doit afficher des nombres)
ros2 topic echo /cmd_vel

# Lister les nœuds actifs
ros2 node list   # → /fsm_navigation ou /bt_navigation

08 — Bilan

Difficultés
rencontrées

Délai de démarrage Gazebo
Le plugin GazeboRosFactory met du temps à s'initialiser. Le spawn du robot échoue si lancé trop tôt. Solution : attendre l'apparition visuelle du robot avant toute commande.
Oscillations FSM
Dans les couloirs étroits, le robot pouvait alterner indéfiniment entre TURN_LEFT et TURN_RIGHT. Résolu par une fenêtre glissante de détection d'oscillation et un forçage de direction.
API Blackboard py_trees 2.x
La migration de py_trees 0.x vers 2.x (Humble) a introduit un nouveau système de Blackboard avec Client et register_key(). L'ancienne API set/get directe ne fonctionne plus.
Angles morts du Lidar
En ne lisant que la zone frontale, le robot pouvait rater des obstacles sur les côtés lors des rotations. Le découpage en 6 zones avec seuils latéraux (DIST_SIDE) a corrigé ce problème.
